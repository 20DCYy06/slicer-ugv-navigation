# 四轮近场感知与 DWA/TEB 实车记录分析

本轮只取回、校验和离线分析用户明确采集的资料，没有修改生产配置、固件或控制链，没有向车端发运动/控制权指令。原始6包及manifest、rosbag.log均已取回，18个文件共404,581,730字节，与车端SHA256全部一致：校验记录（原归档未随仓库收录：`../../.test-results/perception-nav-review-20261026/copy-verification.json`）。bag目录名使用UTC日期，本文日期按UTC+8记录。

## 用户观察与记录范围

- 感知4包依时间顺序对应用户描述的15cm、30cm、50cm、从近处逐渐增至50cm；这是按用户顺序关联，不是程序测得的物体距离。
- 目标物是圆柱形水杯，直径约6.5cm；距离为雷达外壳与杯外壳之间的水平间距。杯高、材质、逐帧位置、光心相对外壳偏移未知，不将原始近点自动标注成杯子。
- DWA用户观察：原地掉头无大平移，后方目标转身后前进，二维目标走弧形，简单障碍绕行可行。TEB用户观察：掉头/后方/侧向困难；未测TEB绕障。

## 1. 近场存在明确的 LIO 软件截断

四包的开始/结束参数快照均为：

```yaml
preprocess/blind: 0.3
slicer_cloud_to_scan/range_min: 0.05
slicer_cloud_to_scan/min_height: 0.04
slicer_cloud_to_scan/max_height: 0.50
```

新取回的车端 `fast_lio/src/preprocess.cpp` 中 `avia_handler` 的非特征提取分支在line/tag检查、每3个有效点抽样后，仅保留 `x*x+y*y+z*z > blind*blind` 的点；`laserMapping.cpp` 将经过预处理/去畸变的 `feats_undistort` 发布为 `/cloud_registered_body`。因此用于导航的点云已经经过30cm三维径向筛选，后面的scan投影即使最小距离设为5cm也无法恢复被删的近点。

源码与数据同时支持这一结论：

- 按实际raw点的line/tag、每3点抽样、0.3m阈值复算，严格0.1ms对齐的747组raw→body帧点数逐帧完全相等。补充758组匹配的最大时间差0.237ms，点数差也全部为0；没有用原始零回波充当有效近物体。
- 15cm顺序对应包中，原始非零近返回每帧约668～783个，LIO body中未见相同距离段。另有8,438个前方近返回满足光心前方x>0.10m、|y|≤0.15m、三维距离<0.29m、base高度落在投影窗内，说明不只是把所有近点当车身；但仍不能把这些点逐个认定为水杯。
- 具体会被每3点抽样选中的有效近点示例为 `laser=(.237,.010,.023)m`，三维距离 `.238323m`；变换到base为 `(.307,.010,.203)m`，高度在投影窗内，位置在arm/self-scan掩码及当前前足迹之外，仍被0.3m距离条件排除。
- 四包的body→filtered同stamp比较没有新增屏蔽点；scan_raw→scan也没有有限点被车身过滤移除。这轮主要近场删点发生在它们之前。
- `filter_size_surf=0.15`用于另一处降采样，body发布点集并不是据此直接体素化后的世界点云；本轮数据不支持把漏点归于15cm体素或5cm地图分辨率。

30cm为光心处三维径向距离，用户观察的约25cm是外壳水平间距，两者不能直接相减或等同。已确认软件近场筛除机制；尚未确认杯子在所有距离/方位的可靠检测率，不能声称仅把阈值调小就完成修复。

另有独立的地图显示机制：当前footprint前端距base为0.27m、雷达配置前移0.07m，雷达前方约20cm仍可能落在配置足迹内，footprint clearing会清除足迹内格子。四包中配置footprint内的lethal格中心均为0；但这不能解释更上游原始点到LIO已经消失。地图格中心统计用最近录制odom变换，最大接收时间对齐差<0.050s，不作为实测障碍间隙。

详细数据：点云分层目录（原归档未随仓库收录：`../../.test-results/near-obstacle-review-20261026/`）、预处理匹配（原归档未随仓库收录：`../../.test-results/near-obstacle-review-20261026/preprocess-count-match.json`）、地图补充（原归档未随仓库收录：`../../.test-results/perception-nav-review-20261026/costmap-summary.json`）。新取源码及生成配置只来自明确路径，见 `.test-results/perception-nav-review-20261026/perception-source/`；源码哈希不单独充当运行二进制身份，运行数据复算另列为证据。

## 2. TEB 确实运行，但控制出口与队友整套行为不同

这次TEB manifest明确记录 `teb_local_planner/TebLocalPlannerROS`，实际时间/路径权重1.5/0.2，forward-drive权重900，线/角上限0.125m/s与0.25rad/s，`min_turning_radius=0`、`max_vel_y=0`。这是标准ROS TEB插件和队友参数的选择性迁移，不是完整复制其导航系统。

本轮已经定位到具体的不兼容，而不是单凭“车没动”推测：

| 本轮记录 | 实际结果 | 关键证据 |
| --- | --- | --- |
| DWA四段：原地π、后方约2m、相对(1,1)、前方2m | 4次均SUCCEEDED，raw负vx为0 | 与用户观察一致；到点仍按既有容差，不是独立尺量验收 |
| TEB原地π | 20.20秒振荡ABORTED | 178/205条raw带负vx；17.79秒因负vx整条拒绝；其中连续片段raw角速为-0.25但nav/final/MCU目标全零 |
| TEB后方约1m | 90.10秒后PREEMPTED | 有前进/转向，但负vx拒绝31.66秒、扫掠拒绝7.64秒；符合超时取消时序，不是一直不动 |
| TEB相对(1,1)两次 | 第一次被取消，第二次无有效全局路径ABORTED | 第二次仅2条零raw，停在全局求路层，不能全部归因于负vx |
| TEB相对(1,0.5) | 8.20秒SUCCEEDED | 本次83条raw无负vx，说明TEB不是每个目标都完全不能动 |
| TEB侧向约2m | 20.10秒振荡ABORTED | 实际记录为相对右侧约(0,-2,-0.785)，192/202条raw带负vx，拒绝19.14秒 |

我方Guard当前规则：任意 `vx<0` 就将整条Twist停止，连角速度一起归零。TEB的前进权重是软约束，实际仍会输出负vx。因此本轮TEB掉头/侧向停滞的主要阻断点在Guard入口，不能说是该时段MCU接受了持续角速度却转不动。这里的负值不全是浮点零，原地段最小达到-0.02m/s。

两包驱动均为body_speed/0x16，0x93 IMU有效位持续健康。本轮最终cmd和MCU接受目标均未出现负vx。没有发现持续的任务外前进；TEB终态后仅约13/39ms的两条命令尾部。没有人员站位时间记录，所以不能将某次正向移动直接归因于“站在车后”。

完整分段和逐秒证据：导航分析（原归档未随仓库收录：`../../.test-results/field-nav-20261026/TEB_DWA_FIELD_ANALYSIS.md`）。两种planner的后方距离、起点和障碍环境不同，不按本表时间做严格性能排名。

## 3. 队友的后退与“先转后走”有独立上层实现

本地已取回的队友源码中，普通导航 `max_reverse` 也为0。区别是其原Guard对负vx清零后保留角速度；我方版本按已有审查后的规则拒绝整条命令。这是同样TEB输出在两套控制出口表现不同的一项真实原因。

队友 `multi_goal_patrol.py` 另有 `BACKUP` 恢复，参数为-0.20m/s、2.2秒、最多2次，向mission输入发布；同时有 `DEPART_YAW`，先按目标方位发纯旋转再进入导航。这些不是标准TEB插件自带的步骤，本工程没有迁入这些状态机或控制通道。源码存在该能力不证明队友当时实车观察必然来自它，但提供了具体可核实来源。

队友快照还使用带B样条平滑的全局规划器，我方按既定任务保留原生GlobalPlanner。双方速度上限、足迹和控制出口也不同，所以“复用TEB”不能表述为全链等效复刻。上述对照基于已收取源码快照，而不是此次同时记录了队友完整运行系统。

## 4. DWA为何会边转边走

给标准move_base一个相对(1,1)目标，是指定目标位姿，没有约定先原地转45°再直行。DWA在短预测窗口对线/角速度组合评分，边转边走可以成为选中的局部轨迹；`yaw`是终点朝向，不是出发前必须先达到的朝向。参见[DWA 1.17.3官方评分实现](https://github.com/ros-planning/navigation/blob/1.17.3/dwa_local_planner/src/dwa_planner.cpp)。弧线符合算法行为，但不能据此说任何大半径弯路都合理；后续应按全局/局部plan与实际轨迹比较，而不是换成TEB就预期自动分段。

当前建议继续以已完成这轮目标的DWA作为现场主线，优先制定近场删点的最小修正/回放验证，再处理TEB与禁倒车出口的兼容性。“先转后走”若要强制执行，应作为明确的行为要求单独选择。以上尚未实施任何修复，尤其没有擅自放宽Guard规则或迁入队友巡航恢复。
