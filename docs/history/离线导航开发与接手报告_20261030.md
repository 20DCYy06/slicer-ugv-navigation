实际完成的开发
1. 独立在线入口
新增：
- slicer_ugv_ros1/src/ugv_bringup/launch/slicer_online.launch
- slicer_ugv_ros1/src/ugv_bringup/launch/slicer_depth.launch
选择复用队友的 Gmapping 与 D455 感知，把它们接入我方现有导航链。没有整体启动队友 BSpline/TEB 那套入口，避免重复的 EKF、Guard、Mux 和 driver。

接线为：现有 LIO/轮速提供 odom→base_link；Gmapping 提供 map→odom；全局 Costmap 在 map 中接收在线地图；局部 Costmap 在 odom 中组合雷达/深度；GlobalPlanner/DWA 经原 Guard/Mux 向底盘提供命令。

默认不启动激光/相机驱动或底盘driver，也不连接真实控制出口；可消费现有传感器或录包输入。传感器、相机及控制连接由已有风格的显式参数选择。新增入口没有目标发送或自动 release 行为。
2. 保留原有参数并解决安装资源问题
在本入口拥有 sensors 的情况下，经我方 wrapper 保留 LIO x/y/yaw + wheel vx、Q(wz)=0.2；在线profile明确使用 xy=0.10m、yaw=0.12rad。现有速度、车体足迹、膨胀参数和 driver/Guard/Mux 生产逻辑保持原样。

队友原入口依赖未被普通安装规则安装的 .runtime。现在将实际需要的9份配置资源复制到我方安装目录结构，保留逐文件来源与 SHA256；未将队友含较高速度和另一足迹的 vehicle.yaml 加载到我方规划器。

官方 XmlLoader 已展开源码布局及模拟 share 安装布局。此项证明资源路径和最终参数能解析，不等于真实 Catkin 安装与运行已经通过。
3. 深度模块适配
复用队友两份脚本到我方 ugv_navigation/scripts/，注明来源，原队友脚本保持逐字节不变。

只处理三个能离线复现的输入问题：未来/滞后的时间、重复/倒序图像、非有限投影内参。沿用原有0.5s时间边界，没有增加比例门限或控制状态机。原有投影、倾角修正、体素处理、hits/rays分工保持不变。

测试包括真实执行 process_latest，仅替换 ROS 传输/时钟/消息封装；正常地面帧仍发布空障碍云和有效清除射线。

全无有效测距时仍沿用原模块发布空云。它不表示观察到了自由空间，也不证明低障碍感知有效。 这与正常“没有障碍、但有有效地面射线”的情况不同。同步相机数据、断流和全无效深度行为仍需后续 ROS 集成/现场验证。
4. ENU 离线预览
新增 slicer_ugv_ros1/tools/preview_enu_goal.py。

支持明确方向的 map←ENU，或 map←odom←ENU 组合；输出 map 坐标和可选目标yaw。没有给目标yaw时不补零或使用飞机姿态。仅使用 Python 标准库，不联网，不调用 ROS Action/Service，不输出自动运动命令。

例如：ENU目标(10,0)，map←ENU平移(2,1)、旋转90°，得到map目标约(2,11)。这只是用给定变换计算，实际ENU原点、外部测量配准和飞机正式协议仍未完成。

地图定位校正不必然意味着map基准改变；odom连续也不意味着地理稳定。跨地图重建、里程计重启等不能仅凭相同frame名称沿用旧配准。
5. 本地开发入口
tools/noetic.sh 增加可选的队友源码只读挂载，用于解析外部包/launch；保留无网络、无设备的测试容器设置，不 source 车端 ARM 的构建目录。

地图范围取舍
队友默认每轴±20m，无法保证任意初始朝向下的场地远目标在网格内。新入口将初始半宽参数化，默认±60m；可按实测场地缩小。

0.05m分辨率下为2400×2400、576万格，是原初始格数的9倍。单个int8栅格数据约5.76MB，不能据此推断整个系统内存。Jetson的CPU/内存/发布时延尚未实测。

全局允许规划经过未知区；局部和Guard维持原检查。扩大边界与允许全局未知都不表示传感器已经观测到那里，也不提供主动探索/死路逃脱保证。原调试速度上限同样保留，尚未做比赛全程时间优化。
